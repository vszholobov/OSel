# Runner

**Для кого:** все, кто запускает ядро или тесты.

**Коротко:** runner (`runner/`) — инструмент на хост-машине, который cargo вызывает вместо запуска ядра. Он собирает образ диска из ELF ядра и запускает QEMU. Поведение настраивается переменными `OSEL_*`. Как устроены тесты — в [отдельной странице](../architecture/testing.md).

## Как вызывается {#invocation}

`.cargo/config.toml` задаёт для таргета `x86_64-unknown-none` раннер `runner/run.sh`. Скрипт собирает и запускает крейт runner под хост-машину (`cargo run --locked` с `--target host-tuple`) и передаёт ему путь к ELF ядра и аргументы QEMU. Путь к скрипту cargo считает от корня репозитория, поэтому `cargo run` работает из любой подпапки.

## Переменные окружения {#env}

| Переменная | Значения | По умолчанию | Что делает |
|---|---|---|---|
| `OSEL_BOOT` | `uefi`, `bios` | `uefi` | какой образ собрать и как загрузить. Пустое значение — то же, что не задано, другое значение — ошибка |
| `OSEL_EXPECT` | любой текст | не задано | режим смоук-теста: загрузить настоящее ядро без окна и завершиться успехом, как только строка с этим текстом появится в последовательном порту. Пустое значение — то же, что не задано |
| `OSEL_TIMEOUT` | целое число секунд больше 0 | 60 | предел для тестовых ядер и режима `OSEL_EXPECT` |
| `OSEL_OVMF_DIR` | путь к папке | папка .ovmf внутри runner | куда скачать и где хранить прошивку UEFI для QEMU |
| `OSEL_RAMDISK` | путь к папке | `ramdisk` в корне репозитория | какую папку упаковать в ramdisk (архив cpio). Относительный путь считается от корня репозитория, а не от текущей папки. Пустое значение — то же, что не задано |

Неверное значение `OSEL_BOOT` или `OSEL_TIMEOUT` — ошибка до запуска QEMU: runner печатает `unknown OSEL_BOOT value …` или `OSEL_TIMEOUT must be a positive number of seconds, got …` и завершается с провалом. Так же runner останавливается, если не собралась программа из `user/` или `user-go/`, если папки ramdisk нет (`ramdisk directory … does not exist, see OSEL_RAMDISK`) или в ней есть что-то кроме каталогов и обычных файлов (`…: only files and directories can go to the ramdisk`).

## Программы из user/ {#user-programs}

Перед упаковкой ramdisk runner собирает каждую программу из `USER_PROGRAMS` и `GO_PROGRAMS` (ниже). Сначала программы из `USER_PROGRAMS` (`runner/src/main.rs`): `cargo build --locked --release --target x86_64-unknown-none` для `user/<имя>/Cargo.toml` в отдельную папку `user/target`, с `-Crelocation-model=static`, потому что ядро загружает только `ET_EXEC`. `RUSTFLAGS`, `CARGO_TARGET_DIR` и `CARGO_BUILD_TARGET` внешнего cargo программе не передаются. Результат добавляется в архив как `/bin/<имя>` с правами `0755`, после файлов из папки ramdisk. Если в этой папке уже есть `bin/<имя>`, runner останавливается с ошибкой `bin/<имя> is in the ramdisk directory and also a program of user/`. Ошибка сборки программы — тоже остановка до запуска QEMU (`building user/<имя> failed`).

В `USER_PROGRAMS` входят `hello` и `clear`. Программа `user/clear/src/main.rs` — отдельный статический ELF: через `write` отправляет ANSI-команды очистки и возврата курсора, затем завершается. Игра запускает её обычным `exec.Command("clear")`; окружение должно содержать `PATH=/bin`.

## Программы из user-go/ {#go-programs}

Так же runner собирает каждую программу из `GO_PROGRAMS` хостовым `go`: `go build -mod=readonly -trimpath` в `user-go/<имя>/` с `CGO_ENABLED=0`, `GOOS=linux`, `GOARCH=amd64`, `GOAMD64=v1` и `GOTOOLCHAIN=local` (ядро загружает статический `linux/amd64` с базовым набором инструкций и не скачивает тулчейн). Результат добавляется как `/bin/<имя>`. Если `go` на машине нет, программа просто не попадает в ramdisk, и тесты, которым она нужна, пропускаются; настоящая ошибка сборки (`building user-go/<имя> failed`) останавливает запуск. CI ставит Go, поэтому там сборка идёт всегда.

`gohello` проверяет горутины и таймеры, `goexec` — запуск дочерних программ и каналы через стандартный пакет `os/exec`. Сквозные тесты — `tests/go_hello.rs` и `tests/go_exec.rs`.

## Настоящий тетрис {#tetris}

После программ из `user-go/` runner собирает `apps/tetris/client` из закреплённого git-подмодуля и добавляет `/bin/tetris`. Параметры Go совпадают с [программами выше](#go-programs), результат сохраняется в `user-go/target/tetris`. Зависимости клиента скачивает обычный Go module cache; `-mod=readonly` запрещает автоматически менять зависимости в `go.mod`, тулчейн автоматически не устанавливается. Workflow релиза дополнительно проверяет, что сборка не изменила файлы зависимостей и подмодуль. Отсутствие Go допускает пропуск, а отсутствие подмодуля при установленном Go — ошибка с командой `git submodule update --init --recursive`.

Для тестового ядра `tetris-*` стандартный ввод QEMU подключается к каналу runner. `TetrisInput` ждёт сообщения клиента с `--trace`, отправляет реальные байты клавиш и требует завершения всего сценария дополнительно к обычным критериям теста. Порядок и проверки описаны в [тетрисе](../architecture/tetris.md#tests).

## Режимы {#modes}

Режим выбирается автоматически (`Mode` в `runner/src/main.rs`):

| Режим | Когда | Что добавляется к QEMU | Чем заканчивается |
|---|---|---|---|
| Run | обычный `cargo run` | ничего, открывается окно | кодом выхода QEMU; если QEMU убит сигналом, кодом 128 + номер сигнала |
| Test | имя ELF оканчивается на `-<16 шестнадцатеричных цифр>`, так cargo называет тестовые бинарники | `isa-debug-exit` на порту `0xf4`, без окна, 128 МБ памяти, ввод отключён от терминала | успехом, только если выполнены критерии ниже; образ диска удаляется |
| Expect | не тест и задана `OSEL_EXPECT` | без окна, ввод отключён от терминала | успехом, как только текст найден; QEMU останавливается |

Во всех режимах QEMU запускается с `-serial stdio -no-reboot`.

Стандартная VGA через EDID предлагает разрешение 1280×1024 (`-vga std -global VGA.xres=1280 -global VGA.yres=1024`), чтобы вместить [консоль с крупным шрифтом](../architecture/drivers/console.md#how). Изменение размера окна QEMU масштабирует готовое изображение, но не меняет число строк и столбцов внутри OSel.

## Аргументы после `--` {#test-args}

Аргументы после `--` у `cargo run` передаются QEMU как есть, например `cargo run -- -s -S`. У тестовых ядер они игнорируются: runner печатает `warning: test arguments are not supported and ignored: …`. Поэтому `cargo test -- <фильтр>` не работает: фильтровать тесты внутри ядра нечем. Один интеграционный тест запускается так: `cargo test --test <имя>`, только модульные тесты библиотеки — `cargo test --lib`.

## Коды выхода тестового ядра {#exit-codes}

| Ядро вызвало | Значение в порт `0xf4` | Код выхода QEMU |
|---|---|---|
| `exit_qemu(QemuExitCode::Success)` | `0x10` | 33 |
| `exit_qemu(QemuExitCode::Failed)` | `0x11` | 35 |
| тройной сбой и перезагрузка при `-no-reboot` | — | 0 |

## Критерии прохождения теста {#pass}

1. QEMU завершился до таймаута, иначе `failed: timed out after 60s` (число — значение `OSEL_TIMEOUT`).
2. Код выхода 33, иначе `failed: qemu exit code Some(35)` или другой код.
3. Если в выводе была строка `Running N tests`, строк, оканчивающихся на `[ok]`, ровно `N`, иначе `failed: M of N tests reported [ok]`. Строка `Running N tests` ищется в любом месте строки: прошивка OVMF может оставить свой текст без перевода строки.
4. Если такой строки не было (ядра с `harness = false`), есть хотя бы одна строка `[ok]`, иначе `failed: no test reported [ok]`.

`[ok]` засчитывается, только если стоит в конце строки, а не внутри сообщения.

## Как заканчивается режим Expect {#expect}

- Строка с текстом найдена — успех, QEMU останавливается.
- Текст не появился за `OSEL_TIMEOUT` секунд — сообщение вида `failed: … not printed within 60s`, где вместо многоточия искомый текст в обратных кавычках.
- Ядро завершилось раньше, например перезагрузилось при `-no-reboot`, — сообщение вида `failed: kernel stopped with … before printing …`.

В режимах Test и Expect вывод ядра пересылается после фильтра: вырезаются управляющие последовательности терминала и строки менеджера загрузки OVMF (`BdsDxe:`), пустые строки самого ядра сохраняются. В интерактивном Run последовательности передаются как есть, чтобы тетрис мог управлять курсором и очищать терминал хоста. Каждая полученная порция сразу сбрасывается через `flush`: частичный кадр без перевода строки не должен оставаться в буфере stdout до конца игры.

## Файлы {#files}

| Что | Где |
|---|---|
| Образ диска | рядом с ELF: `<имя>.uefi.img` или `<имя>.bios.img`; для настоящего ядра — target/x86_64-unknown-none/debug/OSel.uefi.img |
| Прошивка UEFI | папка .ovmf внутри runner, скачивается при первом запуске под UEFI (крейт `ovmf-prebuilt`), в git не попадает |
| Ramdisk | собирается в памяти при каждом запуске из папки `ramdisk/` (или `OSEL_RAMDISK`) и попадает в образ файлом `ramdisk`; отдельного файла на диске нет |
| Уровень логов загрузчика | `Warn`: шаги загрузки не печатаются, только проблемы |

## Где в коде {#code}

- `runner/run.sh` — обёртка для cargo.
- `runner/src/main.rs` — `parse_boot`, `parse_timeout`, `ramdisk_dir`, `pack_ramdisk`, `is_test_binary`, `image_path`, `create_disk_image`, `ovmf_firmware`, `forward_serial_output`, `test_outcome`, `expect_outcome`, `wait_with_timeout`.

## Сетевые тесты {#network}

Runner подключает `e1000e` к пользовательской сети QEMU. Для `tests/network.rs` и `tests/network_game.rs` собирается и запускается `tools/network-fixture/`: настоящие обработчики сервера Tetris, случайный порт на loopback. Адрес гостя передаётся через `/bin/network-test-address`; сервер завершается и забирается при выходе runner. `netcheck` из `user-go/netcheck/` проверяет два клиента и большой поток, настоящий клиент получает сценарий через COM1. Отсутствие Go или ошибка сборки сервера не пропускают эти тесты.
