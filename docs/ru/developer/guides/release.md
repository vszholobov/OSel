# Журнал изменений и выпуск версии

Язык: [Русский](release.md) · [English](../../../en/developer/guides/release.md)

**Для кого:** для разработчиков и агентов, которые открывают PR или выпускают версию.

**Коротко:** каждый PR добавляет строку в раздел «Не выпущено» файла `CHANGELOG.md`. При выпуске раздел получает номер версии, а коммит — тег `vX.Y.Z`. Workflow автоматически собирает и проверяет оба загрузочных образа и публикует их в GitHub Release с контрольными суммами. Документация всегда описывает `master`: версий документации нет, история изменений живёт только в журнале.

## Журнал изменений {#changelog}

`CHANGELOG.md` в корне репозитория ведётся с группами изменений. Сверху всегда раздел «Не выпущено», ниже — выпущенные версии от новых к старым.

Каждый PR добавляет в «Не выпущено» строку в одну из групп, в том числе PR только с документацией или тестами:

| Группа | Что сюда |
|---|---|
| Добавлено | новая возможность |
| Изменено | изменилось существующее поведение |
| Исправлено | исправлена ошибка |
| Удалено | возможность убрана |

Строка пишется для читателя, а не для автора: что изменилось для того, кто запускает или разрабатывает OSel.

## Номера версий {#versions}

Используется формат X.Y.Z с нулевой старшей цифрой: пока версия `0.x`, совместимость ничего не обещает.

- **Средняя цифра** растёт, когда закрыт этап плана: `0.1.0` — этап 1, `0.2.0` — этап 2.
- **Последняя цифра** растёт для исправлений между этапами: `0.1.1`.

Номер версии записан в `version` файла `Cargo.toml`. Ядро показывает версию и коммит при загрузке и на экране паники.

## Как выпустить версию {#release}

1. Убедитесь, что в `master` всё зелёное.
2. В `CHANGELOG.md` переименуйте «Не выпущено» в `## X.Y.Z — ГГГГ-ММ-ДД` (без квадратных скобок, как у `## 0.1.0 — 2026-10-14`) и добавьте над ним новый пустой раздел «Не выпущено».
3. Поставьте `version = "X.Y.Z"` в `Cargo.toml` и обновите запись корневого пакета в `Cargo.lock` командой `cargo check`. Закреплённые зависимости и gitlink `apps/tetris` должны быть закоммичены.
4. Откройте PR с этими правками, после мёржа поставьте тег на коммит мёржа:

   ```shell
   git switch master
   git pull --ff-only origin master
   git tag vX.Y.Z
   git push origin vX.Y.Z
   ```

5. Дождитесь зелёного workflow **release images** в Actions. В [GitHub Releases](https://github.com/vszholobov/OSel/releases) должны появиться `OSel.uefi.img`, `OSel.bios.img` и `SHA256SUMS` с описанием версии и коммита. Это готовые образы без сжатия; пользователю достаточно [скачать образ и записать флешку](../../user/usb.md#image).
6. Если закрыт этап, отметьте это в [плане](../roadmap.md).

## Как проверяется и публикуется релиз {#images}

Workflow `.github/workflows/release.yml` запускается по тегам `v*`. `tools/release.py` допускает только `vX.Y.Z`, сверяет версию с `Cargo.toml`, проверяет, что тег указывает на собранный коммит, и требует непустой датированный раздел версии в `CHANGELOG.md`. Текст этого раздела попадает в описание релиза.

Оба образа собираются в одном checkout из одного ELF ядра в профиле `release`. Rust берётся из `rust-toolchain.toml`, Go закреплён точной версией в workflow. Все сборки Cargo, включая вложенные сборки runner и программ, используют `--locked`; Go использует `-mod=readonly`, версии и суммы из `go.mod`/`go.sum`, а тетрис — коммит git-подмодуля. Установка инструментария происходит только на машине GitHub Actions.

Для каждого режима сначала проверяется загрузка через runner. Затем `tools/check-shell.py --image … --boot … --require-tetris --expected-version … --expected-commit …` запускает уже скопированный образ напрямую в QEMU, без пересборки. Проверяются версия и коммит, оболочка, `hello`, внешняя `clear`, лицензия шрифта в ramdisk, наличие тетриса, два запуска игры, таймер, движение, выход и ввод через COM1/PS2. Отсутствие игры — ошибка. QEMU использует снимки диска и переменных UEFI, поэтому проверка не меняет публикуемые файлы.

Сразу после сборки создаётся `SHA256SUMS`; после проверки обоих образов суммы сверяются ещё раз, чтобы убедиться, что проверка не изменила файлы. Только после успеха загружается артефакт Actions. Задача публикации скачивает его и повторно сверяет суммы. Сначала создаётся черновик GitHub Release с тремя файлами; публичным он становится после успешной загрузки всех файлов. В PR workflow выполняет ту же сборку и проверку образов, но не публикует релиз.

## Как проверить выпуск {#verify}

Скачайте оба `.img` и `SHA256SUMS` из опубликованного релиза в одну папку. На Linux выполните `sha256sum -c SHA256SUMS`, на macOS — `shasum -a 256 -c SHA256SUMS`: оба файла должны получить `OK`. Для повторной проверки загрузки скачанных файлов из корня репозитория:

```shell
python3 tools/check-shell.py --image /tmp/OSel.bios.img --boot bios --require-tetris
python3 tools/check-shell.py --image /tmp/OSel.uefi.img --boot uefi --require-tetris \
  --ovmf-code runner/.ovmf/x64/code.fd --ovmf-vars runner/.ovmf/x64/vars.fd
```

Подставьте пути скачанных файлов. Здесь нужны только Python 3 и QEMU, а для UEFI — прошивка OVMF; runner скачивает её при первом запуске UEFI. Проверка готового образа не вызывает Rust или Go. Для сверки баннера добавьте `--expected-version X.Y.Z --expected-commit <короткий-хеш>` из описания релиза.

## Ошибки выпуска {#errors}

| Что видно | Что делать |
|---|---|
| Тег не совпадает с версией или нет раздела CHANGELOG | исправьте подготовку версии через PR; тег выпуска должен указывать на исправленный коммит |
| Не прошёл один из образов | релиз не публикуется; разберите лог QEMU и исправьте причину |
| Сбой при загрузке файлов в Release | может остаться черновик; удалите только этот неудачный черновик, сохраните тег и повторите workflow через **Re-run all jobs** |
| Release для тега уже существует | workflow не перезаписывает его; для нового содержимого выпускайте новую версию |

## Почему без версий документации {#no-versioned-docs}

Документация описывает текущее состояние `master`. Старое поведение при необходимости смотрят в журнале изменений или в документации на нужном теге прямо в репозитории: `docs/` на теге `vX.Y.Z`.
