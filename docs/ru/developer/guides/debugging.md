# Отладка

**Для кого:** для разработчиков и агентов, которые ищут причину сбоя.

**Коротко:** начните с текста паники: её пишет и красный экран, и последовательный порт, который runner выводит в терминал. Адрес `rip` из паники переводится в место в коде через lldb. Для пошаговой отладки запустите `cargo run -- -s -S` и подключите lldb или gdb к порту 1234. Если машина перезагружается без экрана паники, включите журнал прерываний QEMU `-d int,cpu_reset`.

Всё, что идёт после `--` в `cargo run -- …`, runner передаёт QEMU как есть. Для тестовых ядер так не получится: runner отбрасывает лишние аргументы.

## Вывод в последовательный порт {#serial}

Макросы `serial_println!` и `serial_print!` из `src/drivers/cereal.rs` пишут в COM1. QEMU отдаёт этот порт в стандартный вывод, а runner печатает его в терминал, убирая служебный вывод прошивки OVMF. При панике её текст дублируется в порт строкой `OSel <версия> (commit <хеш>) crashed: …`, так что его можно скопировать, а не переписывать с экрана.

Печать в порт работает в любом месте ядра, в том числе до инициализации экрана. На машине без COM1 (большинство ноутбуков) она молча ничего не делает.

## Разбор экрана паники {#panic-screen}

Что значат поля экрана, описано на странице [Красный экран](../../user/crash-report.md#anatomy). Главное для разработчика:

1. Строка `panicked at <файл>:<строка>` указывает, откуда вызвана паника. Для исключений процессора это всегда обработчик в `src/interrupts.rs`, поэтому смотрите на `rip`.
2. `rip` — адрес упавшей инструкции. Ядро собрано как перемещаемый ELF с адресами от нуля, а загрузчик кладёт его в верхнюю половину адресного пространства. В текущей сборке адрес загрузки — `0xffff800000000000`, поэтому смещение внутри файла ядра равно `rip - 0xffff800000000000`.
3. Найдите функцию по смещению:

   ```shell
   lldb target/x86_64-unknown-none/debug/OSel
   (lldb) image lookup --address 0x18c11
   ```

   Для тестового ядра подставьте его файл: путь печатается в строке `Running tests/<имя>.rs (…)` вывода `cargo test`.

4. Для ошибки страницы (`PAGE FAULT`) смотрите `accessed address` и `reason`. Раскладка адресного пространства описана на странице [Память](../architecture/core/memory.md).

Если адрес загрузки перестал совпадать (смещение указывает в никуда), проверьте его так: найдите `_start` в файле ядра (`llvm-nm target/x86_64-unknown-none/debug/OSel | grep ' _start$'`) и сравните с адресом, на котором отладчик видит точку входа.

## Пошаговая отладка {#debugger}

1. Запустите QEMU так, чтобы он ждал отладчик на порту 1234 и не начинал выполнение:

   ```shell
   cargo run -- -s -S
   ```

2. Во втором терминале подключите отладчик и загрузите символы со сдвигом на адрес загрузки ядра.

   {% list tabs %}

   - lldb (есть в macOS)

     ```shell
     lldb target/x86_64-unknown-none/debug/OSel
     (lldb) target modules load --file OSel --slide 0xffff800000000000
     (lldb) gdb-remote 1234
     (lldb) breakpoint set --name kernel_main
     (lldb) continue
     ```

   - gdb

     На macOS для x86_64 нужен отдельный gdb: `brew install x86_64-elf-gdb`.

     ```shell
     x86_64-elf-gdb
     (gdb) add-symbol-file target/x86_64-unknown-none/debug/OSel -o 0xffff800000000000
     (gdb) target remote :1234
     (gdb) hbreak kernel_main
     (gdb) continue
     ```

   {% endlist %}

{% note tip %}

Если обычная точка останова не срабатывает, используйте аппаратную (`hbreak` в gdb, `breakpoint set --hardware` в lldb). Пока процессор не перешёл в 64-битный режим, программные точки останова на адресах ядра не работают.

{% endnote %}

## Перезагрузка без экрана паники {#triple-fault}

Если ядро упало так, что не смогло показать панику (тройной сбой, triple fault), процессор перезагружается. Runner запускает QEMU с `-no-reboot`, поэтому QEMU просто завершается. Чтобы увидеть, какие исключения были перед этим:

```shell
cargo run -- -d int,cpu_reset -D /tmp/qemu.log
```

Если ядро не падает, окно QEMU останется открытым: закройте его. Без окна и с ограничением времени — так: `OSEL_EXPECT="OSel ready to go!" cargo run -- -display none -d int,cpu_reset -D /tmp/qemu.log`.

В `/tmp/qemu.log` по порядку записаны все прерывания и исключения: номер вектора (`v=0e` — ошибка страницы, `v=08` — double fault), код ошибки и регистры. Последние записи перед `CPU Reset` показывают причину. Список векторов — в справочнике [Векторы прерываний](../reference/vectors.md).

## Скриншот экрана {#screenshot}

Окно QEMU не всегда удобно, например на машине без графики или для агента. Экран можно сохранить в файл через монитор QEMU:

```shell
cargo run -- -display none -monitor unix:/tmp/osel-mon.sock,server,nowait
```

Во втором терминале:

```shell
echo "screendump /tmp/osel.png -f png" | nc -U /tmp/osel-mon.sock
echo "quit" | nc -U /tmp/osel-mon.sock
```

Через тот же монитор можно нажимать клавиши: `sendkey a`, `sendkey shift-1`.

Тестовые ядра печатают результат в порт и выключают QEMU сами, поэтому скриншот там обычно не нужен. Если нужно увидеть экран тестового ядра, запустите его образ напрямую: `qemu-system-x86_64 -drive format=raw,file=<образ> …`. Runner удаляет образы тестовых ядер после прогона, поэтому образ сначала придётся пересобрать.

## Частые ошибки {#errors}

| Что видно | Что делать |
|---|---|
| Точки останова не срабатывают | проверьте сдвиг символов (`--slide`, `-o`) и используйте аппаратные точки |
| `image lookup` ничего не находит | адрес не уменьшен на адрес загрузки или файл ядра от другой сборки |
| QEMU сразу завершается без вывода | тройной сбой, см. [Перезагрузка без экрана паники](#triple-fault) |

Готовые ответы на типичные симптомы — на странице [Что пошло не так](troubleshooting.md).
