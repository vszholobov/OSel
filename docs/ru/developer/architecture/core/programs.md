# Программы

Язык: [Русский](programs.md) · [English](../../../../en/developer/architecture/core/programs.md)

**Для кого:** разработчик и агент, которые трогают загрузку программ или их стартовое состояние.

**Коротко:** программа — статический исполняемый ELF64 для x86_64 из файловой системы, как его собирает Go с `CGO_ENABLED=0`. `program::load` создаёт `UserSpace`, и загрузчик из `osel-core` отображает обнулённые страницы сегментов и копирует в них байты файла. Под вершиной нижней половины отображается стек, его начало заполнено по System V ABI. Как программа запускается — в [пользовательском режиме](user-mode.md).

## Как работает {#how}

### Разбор ELF {#elf}

`elf::parse` (`osel-core/src/elf.rs`) принимает только то, что умеет загрузить, всё остальное — `ENOEXEC`:

- ELF64, little endian, `ET_EXEC` (статический, не PIE), `EM_X86_64`, заголовки программы по 56 байт, их от 1 до 64, и они лежат внутри файла;
- `PT_INTERP` и `PT_DYNAMIC` — отказ: динамической компоновки нет. `PT_TLS` (Go ставит TLS сам через `arch_prctl`), `PT_PHDR`, `PT_NOTE`, `PT_GNU_STACK` и остальные не используются;
- сегменты `PT_LOAD` с ненулевым `p_memsz`: `p_filesz ≤ p_memsz`, байты файла внутри файла, адреса без переполнения от `MIN_USER_ADDR` (64 КБ) до `USER_END`, сегменты идут по возрастанию и не перекрываются, сегмент не бывает одновременно записываемым и исполняемым;
- точка входа лежит в исполняемом сегменте;
- `AT_PHDR` — адрес заголовков программы, если какой-то сегмент загружает их байты из файла, как считает Linux.

Файл читается через `ReadAt`: срез байт или узел файловой системы (`dyn Inode`). Короткое чтение повторяется, конец файла раньше времени — `ENOEXEC`.

### Загрузка {#load}

`elf::load` раскладывает сегменты по страницам (`page_plan`): страница, общая для двух сегментов, получает права обоих, и если из них выходит записываемый код — `ENOEXEC`. Затем через `ProgramMemory` отображает обнулённые страницы и копирует байты файла кусками по странице. Остаток сегмента после `p_filesz` (`.bss`) остаётся нулевым. Сегменты должны кончаться не выше переданной границы и вместе занимать не больше `MAX_PROGRAM_BYTES` (256 МБ), иначе `ENOMEM` ещё до отображения: сломанный `p_memsz` не должен съесть всю память. При ошибке память остаётся наполовину заполненной: вызывающий удаляет всё пространство.

В ядре `ProgramMemory` реализует `UserSpace` (`src/program.rs`): `map_zeroed` — это `UserSpace::map`, `write` — `UserSpace::write_bytes`, который пишет через отображение физической памяти, не глядя на права страниц.

### Стек главного потока {#stack}

`program::load_file` после сегментов отображает `STACK_SIZE` (256 КБ) записываемой неисполняемой памяти под `STACK_TOP`. Последняя страница нижней половины не отображается, страница под стеком — охранник, сегменты программы обязаны кончаться ниже неё. Стек отображается сразу целиком. Сегменты и стек становятся [областями](memory.md#areas) программы, как память от `mmap`; страница-охранник — нет.

### Стартовый стек {#initial-stack}

`initial_stack::build` (`osel-core/src/initial_stack.rs`) раскладывает сверху вниз:

1. 16 случайных байт для `AT_RANDOM`;
2. строки аргументов, затем окружения, каждая с нулём в конце;
3. выравнивание, чтобы указатель стека делился на 16;
4. `auxv`: `AT_PHDR` (если известен), `AT_PHENT`, `AT_PHNUM`, `AT_PAGESZ`, `AT_ENTRY`, `AT_UID`, `AT_EUID`, `AT_GID`, `AT_EGID`, `AT_SECURE`, `AT_RANDOM`, `AT_NULL`;
5. указатели окружения и `NULL`, указатели аргументов и `NULL`, `argc` — на него указывает `rsp`.

`AT_SYSINFO_EHDR` нет: без vDSO Go вызывает `clock_gettime` системным вызовом. Кроме него Go читает из auxv только `AT_RANDOM`, `AT_PAGESZ` и `AT_SECURE`, остальное нужно libc. Без `AT_PAGESZ` Go пошёл бы в `/proc/self/auxv`, без `AT_RANDOM` — в `/dev/urandom`. Строка с нулевым байтом — `EINVAL`, всё вместе больше `MAX_INITIAL_STACK_BYTES` (128 КБ) — `E2BIG`. Случайные байты ядро берёт из счётчика тактов, перемешанного splitmix64: Go ими только засевает хэш-таблицы.

## Программы на Go {#go}

Этап 2 проверен статической программой `user-go/gohello/main.go`: она печатает «hello from go», запускает пять горутин с `time.Sleep`, складывает квадраты их номеров и выходит с кодом 30. Runner собирает её и кладёт в `/bin/gohello`; параметры сборки и поведение без установленного Go — в [справочнике runner](../../reference/runner.md#go-programs).

Сквозной тест `tests/go_hello.rs` запускает программу через `program::run` с `GODEBUG=asyncpreemptoff=1` и проверяет `Stop::Exit(30)`. Он использует общий тестовый фреймворк с проверкой утечек кучи и физических страниц. Без бинарника (`ENOENT`) тест пропускается; CI устанавливает Go и выполняет его в обоих режимах загрузки. Обычный запуск ядра пока запускает `/bin/hello`, а не Go-программу.

Асинхронное вытеснение Go отключено, потому что ядро пока не доставляет сигналы. Заглушки сигналов описаны в [справочнике системных вызовов](../../reference/syscalls.md); nil-разыменование завершает процесс вместо паники Go. Это не отключает [вытеснение потоков ядром](threads.md#preemption).

## Где в коде {#code}

- `osel-core/src/elf.rs` — `parse`, `page_plan`, `load`, `ReadAt`, `ProgramMemory`, `ElfBuilder` для тестов.
- `osel-core/src/initial_stack.rs` — `build`, `AuxValues`, константы `AT_*`.
- `src/program.rs` — `load`, `load_file`, `STACK_TOP`, `STACK_SIZE`, `ProgramMemory` для `UserSpace`.
- `src/memory.rs` — `UserSpace::write_bytes`, `read_bytes`, `page_flags`.

## Инварианты {#invariants}

- Страницы программы отображаются обнулёнными: в них не попадают данные ядра и прошлых владельцев.
- У программы нет страниц ниже `MIN_USER_ADDR`, в последней странице нижней половины и в странице под стеком.
- Записываемых исполняемых страниц у программы нет.

## Блокировки и контекст прерываний {#locks}

Загрузка выделяет память в куче, а `UserSpace::map` и `write_bytes` берут `MEMORY`, поэтому загрузка идёт только из обычного кода ядра, не из обработчиков прерываний.

## Грабли {#pitfalls}

- **Сегменты копируются, а не отображаются из ramdisk:** данные в cpio не выровнены по странице, см. [файлы и ramdisk](fs.md#pitfalls).
- **Строже Linux.** Linux пускает общую страницу кода и записываемых данных (права берёт у последнего сегмента) и требует, чтобы адрес и смещение сегмента совпадали по модулю страницы. OSel первое отвергает, второго не требует, потому что копирует. Go собирает сегменты на отдельных страницах, ему это не мешает.
- **Ошибка в середине загрузки оставляет половину программы.** Откатывать её не нужно: `UserSpace` удаляется целиком и возвращает все страницы.

## Тесты {#tests}

- `osel-core/src/elf.rs` — разбор и загрузка в поддельную память, которая проверяет запись только в отображённые страницы; `AT_PHDR`; таблицы плохих заголовков и сегментов; игнорируемые заголовки Go; права общей страницы; соседние сегменты на одной странице; короткие чтения; 5000 случайных порч файла без паники.
- `osel-core/src/initial_stack.rs` — стартовый стек байт в байт, выравнивание при любом числе аргументов, auxv для Go, `EINVAL` и `E2BIG`.
- `src/program.rs` — программа в настоящем `UserSpace` с правами страниц, `.bss`, стеком и охранниками; плохие программы; нехватка страниц на каждом шаге — `ENOMEM` без утечек; сегмент до самой границы стека.
