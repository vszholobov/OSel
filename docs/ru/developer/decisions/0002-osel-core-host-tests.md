# 0002. Логика ядра в osel-core с тестами на хосте

Язык: [Русский](0002-osel-core-host-tests.md) · [English](../../../en/developer/decisions/0002-osel-core-host-tests.md)

**Для кого:** для тех, кто добавляет код в ядро и решает, куда его положить.

**Коротко:** всё, что не трогает железо (консоль, аллокаторы, карта памяти, разбор клавиатуры, отчёты об исключениях, блокировка), живёт в `osel-core/` и тестируется командой `cargo test-core` на машине разработчика за доли секунды. В ядре (`src/`) остаются порты, ассемблер и глобальные объекты.

**Статус:** принято. **Дата:** 2026-10-11.

## Контекст

Сначала все тесты ядра работали только внутри QEMU: каждый запуск — сборка образа и загрузка, крайние случаи проверять дорого, хост разработчика — Mac на ARM. Ревью нашли ошибки в логике, которые легко ловятся обычными unit-тестами: перекрытые регионы памяти, переполнение адресов, прокрутка консоли.

## Решение

- Workspace: корневой пакет — ядро, участник `osel-core`, `runner` исключён.
- `osel-core` — `no_std` вне тестов, зависит от `x86_64` без функции `instructions`, поэтому собирается на любом хосте.
- Команды: `cargo test-core` и `cargo test-runner` (алиасы в `.cargo/config.toml`), в CI отдельная быстрая задача без QEMU.
- В QEMU остаются тесты того, что требует железа: прерывания, таблицы страниц, экран, падения.

## Рассмотренные альтернативы

- **Только тесты в QEMU.** Отвергнуто: медленно, крайние случаи неудобны, мутационное тестирование показало дыры.
- **Отдельная цель через `per-package-target`.** Работает на nightly, но это нестабильная функция cargo с плохой поддержкой в IDE.

## Последствия

- Новая логика по умолчанию пишется в `osel-core` с тестами, ядро только подключает её. См. [как устроены тесты](../architecture/testing.md).
- Код в `osel-core` не может обращаться к портам и регистрам процессора.
