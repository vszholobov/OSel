# 0016. Анонимная память по первому обращению

**Для кого:** для тех, кто трогает `mmap`, page fault программ или таблицы страниц нижней половины.

**Коротко:** память программы описана областями с правами (`VmaSet`), страница появляется при первом обращении. Отображается только анонимная память. Права страницы — только в её конечной записи, таблицы нижней половины разрешают всё. `PROT_NONE` у страницы с памятью — запись без `PRESENT` с сохранённым адресом. Устройство — в [памяти](../architecture/core/memory.md#areas).

**Статус:** принято. **Дата:** 2026-10-13.

## Контекст

Шаг 9 этапа 2. Рантайм Go при старте резервирует около 1,1 ГБ с `PROT_NONE` (сводки страниц, индекс очистки, арены кучи) и около 40 МБ для чтения и записи, из которых трогает малую часть. Внутри резервов он берёт память через `mmap` с `MAP_FIXED` и ждёт ровно тот адрес. Сборщик отдаёт страницы через `MADV_DONTNEED` и рассчитывает, что потом они читаются нулями. Ошибку `munmap` Go считает фатальной. У QEMU в тестах 128 МБ.

## Решение

- **Области отдельно от таблицы страниц.** `Mappings` (`osel-core`) хранит области и меняет таблицы через интерфейс `PageTables`. Логика и коды ошибок Linux проверяются на хосте против модели, ядро только берёт `MEMORY` на каждую операцию с таблицей.
- **Страница при первом обращении.** `mmap` только записывает область, page fault отсутствующей страницы внутри области с подходящими правами отображает обнулённую страницу и возвращает программу на ту же инструкцию. Ядро, копируя данные программы, отображает нетронутые страницы так же.
- **Только анонимная память.** Файл — `ENODEV`. `MAP_SHARED` с анонимной памятью — то же, что `MAP_PRIVATE`: `fork` нет.
- **Права только в конечной записи.** Все таблицы нижней половины — `PRESENT | WRITABLE | USER_ACCESSIBLE`, как `_PAGE_TABLE` в Linux.
- **`PROT_NONE` без потери данных.** Запись страницы теряет `PRESENT`, но хранит адрес, как `_PAGE_PROTNONE` в Linux. Обходы таблиц смотрят на пустоту записи, поэтому освобождение такой страницы не теряет.
- **Место без `MAP_FIXED` — сверху вниз ниже `MMAP_TOP`** (на 1 ГБ ниже конца нижней половины), подсказка берётся, если свободна. Подсказки Go — `0xc000000000` и дальше через 2⁴⁰ до `0x7fc000000000`, а с Go 1.26 — случайная база кучи ниже 2⁴⁶ — туда помещаются.
- **Сегменты программы и стек — тоже области**, хотя их страницы отображаются сразу: `munmap`, `mprotect` и `MAP_FIXED` работают с ними как с остальной памятью.

## Рассмотренные альтернативы

- **Отображать всё сразу.** Резервы Go заняли бы больше гигабайта. Отвергнуто.
- **`PROT_NONE` — снять флаг `USER_ACCESSIBLE`.** Ломает правило, что страницы нижней половины доступны программе, и неотличимо от настоящего нарушения прав. Отвергнуто.
- **`PROT_NONE` — снять страницы.** Данные пропали бы при возврате прав. Отвергнуто.
- **Области внутри `AddressSpace` в `osel-core`.** Тогда изменение областей шло бы под `MEMORY`, а области выделяют память в куче, что внутри `with_memory` запрещено. Отвергнуто.
- **Отображение файлов.** Go статической сборки его не использует. Отложено.

## Последствия

- Нехватка страниц при первом обращении заканчивает программу с page fault, а не с `ENOMEM`: обещанная `mmap` память может не найтись, как при overcommit в Linux.
- Буфер системного вызова отображается целиком до копирования: `read` с огромным `count` в свежую память отобразил бы много страниц. `read` ограничен 64 КБ.
- Пока у процесса один поток, области и таблица без своей блокировки. С `clone` и общим адресным пространством (шаг 10) `fault`, проверка с копированием и `munmap` должны идти под блокировкой пространства.
- Копирования при записи нет: без `fork` оно не нужно.
