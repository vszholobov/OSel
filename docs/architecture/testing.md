# Как устроены тесты

**Для кого:** разработчик и агент, которые пишут или чинят тесты.

**Коротко:** тесты идут на трёх уровнях. Чистая логика в `osel-core` и runner тестируется обычным `cargo test` на хост-машине за доли секунды. Всё остальное — тестовые ядра, которые runner загружает в QEMU в режимах UEFI и BIOS. Ядро сообщает результат через последовательный порт и код выхода QEMU. Каждый тест ядра проверяется на утечки кучи. Как добавить тест каждого вида — в [рецепте](../guides/testing.md).

## Три уровня {#levels}

| Уровень | Команда | Где код | Что проверяет | Нужен QEMU |
|---|---|---|---|---|
| Логика ядра | `cargo test-core` | `#[test]` в `osel-core/src/` | консоль, аллокаторы, карта памяти, клавиатура, отчёты, спинлок | нет |
| Runner | `cargo test-runner` | `#[test]` в `runner/src/main.rs` | разбор вывода, коды выхода, таймауты | нет |
| Ядро | `cargo test` | `#[test_case]` в `src/`, файлы в `tests/` | всё, что трогает железо: прерывания, страницы, падения | да |

Алиасы `test-core` и `test-runner` заданы в `.cargo/config.toml`. Они собирают под хост (`--target host-tuple`), потому что по умолчанию сборка идёт под `x86_64-unknown-none`.

## Тесты ядра в QEMU {#kernel}

Каждый тестовый бинарник — отдельное ядро:

- **модульные тесты** — функции `#[test_case]` в `src/`, собираются в одно ядро вместе с библиотекой; точка входа `test_kernel_main` в `src/lib.rs`;
- **интеграционные тесты** — каждый файл в `tests/` — своё ядро. Файл с собственной функцией `main` без тестового фреймворка помечается `harness = false` в `Cargo.toml`.

Cargo запускает каждый бинарник через runner (`runner/run.sh`), runner собирает из него образ диска и загружает в QEMU с устройством `isa-debug-exit`. Ядро завершает QEMU записью в порт `0xf4` (функция `exit_qemu` в `src/qemuno.rs`): код `0x10` — успех, QEMU выходит с кодом 33; код `0x11` — провал, QEMU выходит с кодом 35. Подробности — в [справочнике runner](../reference/runner.md).

## Фреймворк testosterone {#testosterone}

Модуль `testosterone` (`src/testosterone.rs`) заменяет стандартный тестовый фреймворк, которого в `no_std` нет:

- `test_runner` печатает `Running N tests`, запускает тесты и выходит из QEMU с успехом;
- каждый тест печатает `имя...\t`, а после успеха `[ok]`;
- `test_panic_handler` печатает `[failed]` и текст паники и выходит с провалом. Если последовательный порт был занят, он освобождает его блокировку (`force_unlock`) и печатает обычным `serial_println!`. Только при вложенной панике он пишет напрямую в порт через `emergency_print`.

### Проверка утечек {#leaks}

`Testable::run` в `src/testosterone.rs` берёт `in_use()` у кучи (`osel-core/src/heap.rs`) перед каждым тестом и после него. Если число разное, тест падает с сообщением `the test leaked N heap bytes`. Блоки, лежащие в кэше аллокатора, утечкой не считаются. Проверка есть только у тестов `#[test_case]`: ядра с `harness = false` и `panic_test!` её не делают. Тест `tests/leak_detection.rs` проверяет, что утечка действительно ловится.

### Тесты, которые ждут падения {#panic-test}

Макрос `panic_test!` создаёт ядро, которое выполняет тело теста и проходит, только если тело упало с паникой, содержащей все ожидаемые фрагменты. Внутри работает `expect_panic`:

1. показывает экран паники; если это вложенная паника, сразу проваливает тест через `emergency_print`;
2. форматирует сообщение в `FixedBuf` без кучи, потому что паника может прийти из аллокатора;
3. проверяет, что сообщение содержит все фрагменты, и если задан `EXPECTED_RIP`, то и строку `rip: <адрес>`;
4. проверяет экран: левый нижний пиксель красный, в первой строке нарисован заголовок «OSel crashed :(», во второй — строка «OSel <версия>, commit <хеш>». Без framebuffer проверка экрана пропускается.

`EXPECTED_RIP` записывается из ассемблерной вставки прямо перед падающей инструкцией, примеры — `tests/invalid_opcode.rs` и `tests/divide_error.rs`.

## Как runner решает, прошёл ли тест {#pass}

Runner сверяет код выхода QEMU с тем, что ядро напечатало: число строк `[ok]` должно совпасть с объявленным `Running N tests`, а тест без фреймворка должен напечатать хотя бы один `[ok]`. Точные правила, коды выхода и сообщения — в [справочнике runner](../reference/runner.md#pass).

## CI {#ci}

Какие задачи CI что запускают — в [тулчейне и CI](../guides/toolchain-and-ci.md). QEMU в CI работает без аппаратного ускорения KVM, поэтому тесты со временем допускают широкий разброс, а включение KVM записано в [техдолг](../debt.md).

## Грабли {#pitfalls}

- **`cargo test -- <фильтр>` не работает**, см. [справочник runner](../reference/runner.md#test-args). Один интеграционный тест запускается так: `cargo test --test <имя>`.
- **Тестовые бинарники лежат не в папке deps.** Свежий cargo кладёт их в target/x86_64-unknown-none/debug/build/osel/<хеш>/out. Runner узнаёт тест по хешу из 16 шестнадцатеричных цифр в имени файла (`is_test_binary` в `runner/src/main.rs`).
- **Порядок тестов важен.** Тесты в одном ядре разделяют общее состояние: позицию курсора консоли, выданные страницы, буфер клавиатуры. Тест не должен рассчитывать на чистую систему.
- **Паника в проверке утечек** приходит после того, как тест напечатал своё имя. В выводе это выглядит как падение самого теста.

## Тесты {#tests}

- `tests/leak_detection.rs` — проверка утечек ловит утечку.
- `tests/nested_panic.rs` — вложенная паника распознаётся.
- Тесты runner в `runner/src/main.rs` — критерии прохождения.
