# Тетрис

**Для кого:** для разработчика, который меняет игру, её сборку или сквозной тест.

**Коротко:** OSel собирает настоящий Go-клиент из подмодуля `apps/tetris` и запускает `/bin/tetris --single`. Игра работает без сети, использует `/dev/tty` и запускает обычную дочернюю `/bin/clear`. Контрольная точка — `cargo test --test tetris` в обоих режимах загрузки.

## Как работает {#how}

Подмодуль указывает на конкретный коммит репозитория [Tetris](https://github.com/vszholobov/Tetris), а не на движущуюся ветку. Одиночный режим добавлен в [PR №16](https://github.com/vszholobov/Tetris/pull/16). Перед сборкой нового клона нужен `git submodule update --init --recursive`.

Общий движок `lib/field` обслуживает и сервер, и локальную игру; `lib/single` управляет падением, закреплением фигур, очисткой строк и концом игры. Сетевой режим запускается без аргументов. Одиночный клиент использует `--single`, а для воспроизводимой последовательности фигур — `--seed N`.

Клиент читает `/dev/tty` через `go-tty` в отдельной горутине. `Raw()` выключает построчный ввод, эхо и обработку сигналов терминалом; Ctrl+C приходит как байт. Другая горутина рантайма обслуживает таймер падения. Исходные режимы терминала восстанавливаются при выходе.

Вызов `clear` сохранён: Linux/macOS запускают внешнюю команду, Windows — `cmd /c cls`. В OSel поиск идёт по `PATH=/bin`, а `/bin/clear` — отдельный исполняемый файл из ramdisk. Ошибка запуска очистки завершает одиночный клиент с сообщением и ненулевым кодом.

Поле рисуется символом `#`: для игры не нужна кириллица. Клиент выводит команды ANSI `H` (начало экрана), `K` (очистка остатка строки), `?25l` и `?25h` (курсор). Управление: `a`/`d` — влево/вправо, `s` — вниз, `q`/`e` — поворот; `x`, Escape или Ctrl+C — выход.

## Запуск и сборка {#run}

Параметры сборки и ramdisk описаны в [справочнике runner](../reference/runner.md#tetris). Настоящее ядро после строки готовности запускает игру с `PATH=/bin`, `TERM=xterm`, `GODEBUG=asyncpreemptoff=1`. После выхода возвращается к вводу клавиатуры.

## Где в коде {#code}

- `.gitmodules` и gitlink `apps/tetris` — источник и закреплённая версия игры.
- `runner/src/main.rs` — `build_tetris`, `TetrisInput`, сборка и сценарий ввода.
- `src/main.rs` — `run_tetris`, запуск настоящим ядром.
- `tests/tetris.rs` — запуск клиента в тестовом ядре.

## Инварианты и грабли {#pitfalls}

- Смена версии игры — явное обновление gitlink; CI получает подмодули рекурсивно.
- Отсутствующий подмодуль при установленном Go — ошибка сборки, а не тихий пропуск игры.
- Без Go бинарник не попадает в ramdisk, тест сообщает `TETRIS SKIP: Go is not installed`. Runner разрешает пропуск только если сам не собрал бинарник; ошибка поиска уже собранной игры не маскируется под отсутствие Go. CI устанавливает Go, поэтому там игра проверяется обязательно.
- `GODEBUG=asyncpreemptoff=1` нужен до реализации доставки сигналов; аппаратное вытеснение потоков остаётся включённым.
- Игровые управляющие последовательности очищают экран. В тестах runner удаляет их из журнала; интерактивный Run передаёт их как есть, поэтому игра видна и в окне QEMU, и в терминале хоста.

## Проверки {#tests}

В репозитории игры `go test -race ./...` в `lib` и `client` проверяет движение, стены, повороты, очистку строк, очки, воспроизводимость, конец игры и формат кадра. Кросс-сборки покрывают Linux, Windows и macOS; они не заменяют запуск на этих системах.

`tests/tetris.rs` запускает игру с `--single --seed 2 --trace`: первая фигура имеет форму L, поэтому поворот действительно меняет поле. Runner ждёт `TETRIS READY`, затем настоящий `TETRIS TICK` без ввода: это проверяет, что блокирующее чтение не остановило таймер. Далее отправляет `a`, `d`, `s`, `q`, `e`, дожидаясь подтверждения `changed=true` после каждого нажатия; клиент получает этот флаг сравнением состояния игры до и после команды. Последним runner посылает `x` и требует `TETRIS EXIT`. Одного успешного кода выхода для прохождения недостаточно. Общий тестовый фреймворк проверяет возврат страниц и кучи.

Сценарий runner имеет тесты на порядок подтверждений, повторные/чужие строки, очистку ANSI и пропуск без Go. Оба режима прошивки используют один сценарий.
